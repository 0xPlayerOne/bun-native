# macOS input target verification

> **Status (2026-11-05):** the hosted development and AOT macOS input scenarios
> described below have since passed; see
> [native platforms](native-platforms.md#hosted-paint-os-input-and-assigned-device-evidence).
> This record is otherwise kept as written.

The controller must authorize the exact native window that would receive a mouse-down, not the first rectangle containing the point. An opaque, on-screen window may explicitly ignore mouse events. Its rectangle can cover the application while the actual input target is still the application.

The macOS helper (`scripts/quality/native-platform-macos.m`) uses AppKit's documented `+[NSWindow windowNumberAtPoint:belowWindowWithWindowNumber:]` with window number zero. The controller is a plain command-line process, so the helper first initializes its AppKit connection with `[NSApplication sharedApplication]` and requests no activation. Without that step, the query returns zero even for a visible, input-taking window owned by another process. It converts the measured global Quartz point to global AppKit coordinates using the primary display's logical height. It independently matches the returned window number against current Quartz owner, bounds and opacity metadata. Unknown, stale, duplicate, inconsistent, foreign and same-process-but-different windows reject. Foreground and target checks run before each of the three pointer events. Posting remains `CGEventPost(kCGSessionEventTap)`; no permission is requested, no alternate posting route is attempted, and no application/input deadline changes.

## Controls and evidence

`tests/native/macos-input-events.m` verifies actual SDK event construction and bounded pure identity, geometry, coordinate-conversion and diagnostic controls without posting input. `tests/native/macos-window-hit.m` creates two small task-owned windows and verifies the actual WindowServer/AppKit distinction: an ignored overlay is accepted, an input-taking overlay from the same process is rejected, and the uncovered owned target is accepted. Both windows are closed on success or failure. The control does not post keyboard/pointer events or change another application's activation or system permissions. `tests/native/macos-cross-process-hit.m` spawns a separate owner process with one opaque window. It verifies that the initialized helper selects and authorizes that foreign window for its real owner PID. It also verifies that the helper rejects the same window when the controller's own PID is claimed, and that the foreground application does not change. It posts no input.

The same owned-window control fails at the intended authorization boundary with the preceding rectangle-only helper and passes with the corrected helper. The first version of the _new control_ observed a hit before its ignored overlay had become visible, so both variants failed its visibility precondition. That failed attempt remains distinct from the corrected control's bounded visibility rendezvous. This does not extend any existing application deadline or retry a failed native test.

`tests/native/evidence/platform-macos-hit-testing.json` binds the source, actual SDK/compiler, controlled outcomes and raw result hashes. These results establish the guard's semantics on the connected Mac. The recorded hashes describe the source at that run. The helper has since gained the AppKit initialization described above, so its current hash no longer matches the record. **They do not establish GPUI input delivery.** Required hosted development and genuine AOT scenarios still require exact owned process/window identity, three pointer activations, 96 nonce edits, nine complete native paints, joined shutdown and zero ownership counters in each mode. Historical unsuccessful native attempts remain recorded separately.

**Update (2026-11-05):** CI now compiles all three controls with `-Werror` against the hosted `macos-15` SDK and runs them in the "Build the bounded macOS OS controller" step of [`native-platforms.yml`](../.github/workflows/native-platforms.yml), before the development and AOT input scenarios. The `Validation / Gate` job in [`bun-native.yml`](../.github/workflows/bun-native.yml) requires that lane. [Native platforms](native-platforms.md) holds the run history and failure records.

Reference: Apple's `NSWindow.windowNumber(at:belowWindowWithWindowNumber:)` documentation explicitly describes mouse-down hit testing, including transparent pixels and windows with `ignoresMouseEvents`.
