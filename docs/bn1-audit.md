# BN1 bridge, ownership and engineering audit

**Audit date:** October 31, 2026. This review covers the actual requirements in [#219](https://github.com/0xPlayerOne/bun-native/issues/219), [#228](https://github.com/0xPlayerOne/bun-native/issues/228), [#229](https://github.com/0xPlayerOne/bun-native/issues/229), [#232](https://github.com/0xPlayerOne/bun-native/issues/232), [#252](https://github.com/0xPlayerOne/bun-native/issues/252) and [#253](https://github.com/0xPlayerOne/bun-native/issues/253). It reviews implementation and executable negatives, rather than treating the architecture documents as proof.

**BN1 is complete for its documented Linux native scope.** The shared public core, protocol-v2 transactions and input revisions, bounded native/process/callback queues, development and inspected AOT fixtures, and process-failure tests merged in [PR #271](https://github.com/0xPlayerOne/bun-native/pull/271). The complete [required hosted run 41224338023](https://github.com/0xPlayerOne/bun-native/actions/runs/41224338023) passed. The final release evidence below is retained independently of the earlier local development-host diagnostics. Neither establishes macOS/Windows GUI support or long-duration leak freedom. The [BN0 release baseline](bn0-audit.md) describes an earlier protocol-v1 workload and retains its original provenance.

## Finding: continuously ready native commands starved input and paint

### Why the existing bounds were insufficient

The native reader already bounded its queue to 64 commands, and the Bun transport bounded pending requests to 128. Those bounds constrained retained work but did not constrain how long the GPUI thread could remain inside one future poll. The previous `while commands.recv().await` loop dispatched each command through synchronous `cx.update` calls. A continuously replenished queue could keep every receive immediately ready.

This is supported by the pinned implementation, not an assumption about all async runtimes. [async-channel 2.5.0](https://docs.rs/async-channel/2.5.0/src/async_channel/lib.rs.html) returns an available item immediately. GPUI's pinned [AsyncApp::update](https://github.com/zed-industries/zed/blob/ba63a022c9a22ca66d68ef2a8f0bb9b5b0a9984d/crates/gpui/src/app/async_context.rs) synchronously applies updates and flushes effects; its [application effect loop](https://github.com/zed-industries/zed/blob/ba63a022c9a22ca66d68ef2a8f0bb9b5b0a9984d/crates/gpui/src/app.rs) schedules frames. On Linux, the [foreground runnable](https://github.com/zed-industries/zed/blob/ba63a022c9a22ca66d68ef2a8f0bb9b5b0a9984d/crates/gpui_linux/src/linux/platform.rs) runs as one calloop idle callback until that future suspends. None of these paths preempts the continuously ready loop between commands.

### Bounded reproduction and correction

The diagnostic mounts a 1,031-node real tree: the ordinary six visible nodes, one filler box and 1,024 empty text nodes. It keeps up to 128 legal single-label-update commands in flight for a three-second producer interval, replenishing only acknowledged work. An independent XTest controller injects one text edit about half a second into the stream. The sequential control uses the same tree with one acknowledged request and an explicit one-millisecond application yield.

The correction in [native main](../native/gpui-host/src/main.rs) processes at most 16 commands or four milliseconds before awaiting a nonzero one-millisecond GPUI background timer. The timer is outside `cx.update`, so one transaction still validates and commits atomically. FIFO request order, queue bounds and immediate finishing behavior are preserved. A zero timer or a foreground priority change would not provide the required suspension in this pinned scheduler.

These are four **single, instrumented, development-host diagnostics** on Linux x64/Xvfb with llvmpipe, Mesa 25.2.8 and LLVM 20.1.2. They are observations for a reproducible correctness defect, not statistical performance estimates:

| Host and producer                  | Input injection to observed Bun edit | Acknowledged commands | Elapsed stream including drain | Native paint during production                  |
| ---------------------------------- | -----------------------------------: | --------------------: | -----------------------------: | ----------------------------------------------- |
| Original host, 128 pending         |                          2,678.71 ms |                 3,478 |                    3,118.97 ms | No; revision jumped from 9 to 3,487 after drain |
| Original host, sequential control  |                             59.69 ms |                   135 |                    3,039.00 ms | Yes                                             |
| Corrected host, 128 pending        |                            103.69 ms |                   484 |                    3,794.06 ms | Yes                                             |
| Corrected host, sequential control |                             59.85 ms |                   157 |                    3,032.16 ms | Yes                                             |

The original host hash is `8a221ff318aa0a3ee0bfff95bc243dc0091d3c0a2af97347ab3bc550cc3ad40e`; the corrected host hash is `55d2b9312529a01ccc3c4720f03040c4d685e7d51d9b7ece160f8b8e64ad7a49`. Both are development builds from the pinned GPUI/Rust toolchain. The comparison used the same temporary reproducer and native tree/input behavior; the checked-in regression adds stronger final-state assertions. All four runs acknowledged their submitted commands, exited zero and required no cleanup termination or survivor reaping.

The fixed host spends UI time on real painting and input that the old loop starved. Therefore its lower acknowledgement count is not hidden or presented as a throughput speedup. The producer interval and stream drain are separate, and no acknowledgement rate assumes both finished in exactly three seconds. Timer wakeups and quantum choices remain measurable tradeoffs; these observations justify the fairness correction, not universal optimality of the constants.

### Regression oracle

[tests/native/scheduling.ts](../tests/native/scheduling.ts) requires the actual input event while `producerActive` is true. The independent [diagnostics driver](../scripts/quality/native-diagnostics-linux.py) additionally observes native paint traversal before production stops. Large-tree evidence may omit the complete node array at the record limit; those records establish traversal/revision progress only. The final batch removes the filler subtree, updates the label, reorders the surviving label ahead of the heading, and requires the complete six-node native snapshot with the original input value preserved.

The checked-in regression was also run against the preserved original host. It failed specifically with `Native input was starved until the command producer stopped`, returned exit one, and still left no live or unreaped children. The corrected host passed in development and through its separately inspected machine-code AOT executable, including the final reorder/input snapshot. This is a meaningful negative control, not a passing test inferred from inspection of the new timer.

## Actual native startup and crash containment

[tests/native/fault.ts](../tests/native/fault.ts) exercises the public API against the actual GPUI executable. It does not use the headless protocol peer.

The startup scenario supplies an invalid display. It requires transport EOF or native-process exit before the request timeout; a generic exception, missing executable or request timeout cannot satisfy the assertion. The initial development-host run rejected after 29.85 ms with `ProtocolError: Native output closed before shutdown`. This is startup-failure containment, not a successful window test.

The crash scenario first creates a real native window and receives an OS-injected click. Its public listener intentionally remains unresolved. The controller verifies the window PID belongs to the launched process tree, that the PID's start time still matches, and that `/proc/PID/exe` names the explicit native host. It sends SIGSTOP only to that child, waits for the stopped state, requires two pending application transactions and one active callback, then verifies identity again before SIGKILL.

Both pending transactions and `app.closed` must reject with the same transport-exit error. The listener's signal must abort, `window.closed` must resolve, and all six public diagnostics must return to zero. The test application then exits zero; the killed host is recorded as the injected fault, not relabeled as a clean native exit. Source and host fingerprints, bounded logs, identity-checked cleanup and observed survivor checks are retained. The three focused real-process safety tests reject a foreign child, a changed PID identity and a wrong executable before any fault signal.

The development and separately inspected machine-code AOT startup/crash fixtures passed against the corrected host. These results establish the tested Linux process-failure behavior. They do not prove recovery from arbitrary in-process memory corruption, sanitizer cleanliness, a crash-report redaction service or native behavior on another operating system.

## Ownership, security and package review

The native model prepares a complete candidate tree before updating GPUI entities. Monotonic session identities and owner checks reject stale/cross-window references; rejected candidates do not advance the committed graph or identity watermark. Input revisions are independent of tree revisions. A stale input set fails atomically, while unrelated tree changes preserve newer edits. The actual stale-input fixture and full native paint assertions exercise the same rule below the public core's local validation.

The public core owns listener registrations through abort controllers and removes queued callbacks when a node/listener/window is revoked. It ingests native events separately from awaiting user callbacks. Headless edge tests deliberately hold one callback unresolved while processing another window's input and close; they test callback ordering, queue overflow, reentrant replacement and old unsubscribe closures. The real 1,000-cycle fixture adds native create/update/dispose, 3,000 listener registrations and OS-close cancellation. WeakRef observations complement explicit public strong-ownership counts; neither substitutes for native allocator or long-running leak analysis.

The process/ABI boundary remains an availability and contract boundary for a trusted local application. It is not authentication or a restriction on Bun filesystem, subprocess, network or FFI access. The host accepts a finite tree protocol, not arbitrary JS/HTML/CSS/native function addresses. The shared security corpus and native parser reject malformed shapes, unsupported sensitive-service opcodes, invalid identities and bounds. Future service grants and updater/package integrity remain linked to [#255](https://github.com/0xPlayerOne/bun-native/issues/255) and [#247](https://github.com/0xPlayerOne/bun-native/issues/247), with cross-platform artifact qualification in [#246](https://github.com/0xPlayerOne/bun-native/issues/246).

The source layering is `core → runtime → protocol`, with core also consuming portable protocol contracts; only runtime imports platform process APIs. The AST boundary check includes type imports/re-exports, dynamic imports and CommonJS loads, rejects undeclared/unused package dependencies and private subpaths, and requires an explicit policy for new packages. It is a scoped dependency check, not a whole-program security sandbox or complete dead-code detector.

Manual export review removed four unused protocol re-exports: `MAX_DEPTH`, `MAX_NODES_PER_WINDOW`, `MAX_TEXT_BYTES_PER_WINDOW` and `MAX_WINDOWS`. Their internal limits remain enforced. `MAX_OPERATIONS` remains because the protocol tests consume it. Unnecessary declaration exports were also removed. The public package's type/error exports are intentional consumer surface, not classified as dead solely because the implementation does not import its own public entry point.

The missing framework contract evidence was addressed with [framework-consumers.ts](../tests/types/framework-consumers.ts), using pinned Solid 1.9.18, React 19.3.1 and React declarations 19.3.0. These development dependencies exercise two consumers of the same public core. They introduce no framework-specific Rust host or duplicate native primitive and do not claim that a Solid/React renderer is implemented.

## Memory and measurement interpretation

The lifecycle fixture records process memory and ownership checkpoints, all 1,000 cycle acknowledgement observations, sampled callback/subtree WeakRefs, and three sparse forced-GC `bun:jsc` heap snapshots. Whole-heap category walks run before cycles, after cycles and after shutdown, outside the timed cycle workload. The report retains raw category counts, protected counts, before/after deltas and the time spent collecting each snapshot. The updated fixture passed in development and AOT against the corrected host: all public ownership counts were zero after close, every sampled cycle callback/subtree handle was unreachable after collection, and the launch listener was unreachable. Each of the three heap walks took 0.52–0.95 ms in these runs. The two correctness runs ran concurrently, so their cycle timings are not a matched performance comparison. It also states that retained WeakRefs, timing arrays and the snapshots themselves contribute to the observed live heap. For example, the category reports retain 4,002 WeakRef objects after shutdown, of which 4,000 were deliberately created to observe callback/subtree reachability; that count is not evidence that the referenced application objects remain alive.

Live-cell counts are not total allocations or allocation rates, and JavaScript heap observations do not measure Rust/GPUI or GPU allocation. The actual native event-stress fixture separately delivers 1,000 XTest edits, verifies every contiguous event/input revision and intermediate value, then requires a complete final paint and OS close. Its application-observed interval includes instrumented delivery and observation work; it is not a per-keystroke dispatch or presentation-latency distribution. [The bridge benchmark](../benchmarks/bridge.ts) measures acknowledged individual/batched mutations separately with evidence instrumentation disabled. [The repeated startup/RSS runner](../benchmarks/NATIVE_BASELINE.md) uses matched release hosts and descriptive distributions with explicitly uncontrolled caches.

The separate [native allocation diagnostic](../benchmarks/ALLOCATIONS.md) uses
standard Heaptrack interception on the actual owned GPUI process while the same
1,000-cycle public fixture runs. An initial development-host diagnostic observed
760,502 allocation calls and 88,675 temporary allocation calls, with JSON key and
value construction among the dominant call stacks. That profile includes host
startup, evidence logging, software rendering and shutdown. Its 83.00M peak
traced heap and 625.95K outstanding-at-exit quantities retain Heaptrack's display
units; the latter does not by itself establish a leak. It does not count Bun or
GPU allocations. The required CI job repeats this diagnostic with the release
host under both application modes and retains complete compressed traces,
bounded hotspot reports and exact tool/source/artifact hashes.

The executor was recycled after the local audit. Source and checked-in summaries
survived, but temporary raw diagnostic directories did not. Those local results
remain historical observations; they are not a substitute for the required
retained hosted evidence from the final source. No missing raw sample has been
reconstructed from its summary.
