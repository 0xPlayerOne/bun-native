# Inspecting the Bun AOT executable

The Linux BN0 application contains a compiled-program record and records the JIT compiler as removed. Its JavaScript interpreter remains present. These are separate properties: an AOT flag alone does not establish JIT omission, and JIT omission does not establish that every possible runtime-generated string is rejected.

## Source-backed interpretation

All source references below use Bun revision `da867c60bf0bcbf9d6d36994f8ca0efa42075115`, matching `toolchain.json`.

- [`engine.def`](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/features/engine.def#L1-L11) declares JIT, interpreter, built-in source text and image compiler in that order. The [feature generator](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/scripts/build/trim/features.ts#L253-L277) numbers engine features from zero.
- [`all_outside_compiled_programs`](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/removable_features/lib.rs#L137-L142) includes the JIT and command-line compiler tools. The [default retention decision](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/decide.rs#L163-L178) excludes these even without `--trim`, unless a used feature requires them. Therefore inspection must check the emitted executable, not assume all AOT programs have the same retained runtime.
- The [removal-state layout](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/removable_features/state.rs) is a 536-byte record in the named `.bun_features` ELF section, `__TEXT,__bun_features` Mach-O section, or `.bunfeat` PE section. Its 512 feature bytes start at offset 24. The [state enum](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/removable_features/lib.rs#L30-L36) defines zero as present, one as unused and two as explicitly requested removal.
- The [image rewrite](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/apply.rs#L33-L80) removes relocations, fills uncut removed regions with traps or zeroes, cuts removable file ranges, and records the decision. The [state-writing code](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/trim/apply.rs#L347-L369) writes each feature's removal value. The general trim flag can remain zero when only compiler tools and the JIT are removed; it is not a substitute for reading the feature bytes.

## Reproducible checks and limits

`experiments/aot-gpui/run.ts` compiles and executes the same interop source in development, AOT and deliberately non-AOT modes. It requires JIT removal records in AOT and a present JIT in the control on each target. `build-window.ts` applies the same removal check to the actual application and records the result in its manifest. Both retain the interpreter state explicitly.

`inspect-runtime.ts` locates the state through the executable's section table. Supported decoders are little-endian ELF64, thin Mach-O64 (x64/arm64), and PE32+ (x64/arm64). Mach-O uses bounded `LC_SEGMENT_64` commands and section-to-segment address mapping; PE uses the image base, section RVA and virtual size separately from padded raw-file size. Layout references are the pinned Bun [Mach-O](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/exe_format/macho.rs) and [PE](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/exe_format/pe.rs) readers, plus Apple's [Mach-O structures](https://github.com/apple-oss-distributions/xnu/blob/main/EXTERNAL_HEADERS/mach-o/loader.h).

All formats require exactly one named, aligned, read-only, file-backed state record. Removed-range pointers are relative virtual addresses and must resolve to one unambiguous read-only section. The decoder rejects truncated and overflowing ranges, unknown removal states, invalid record sizes, unsupported object/fat/32-bit images and missing or duplicate sections. Synthetic tests exercise malformed metadata and convincing magic outside the named section; separately compiled real executables establish the AOT/control result. This is a decoder for the pinned compiler's artifact contract, not a general-purpose executable security validator.

The first hosted macOS run exposed an actual pinned-Bun format detail: AOT trimming splits a Mach-O segment into numbered pieces such as `__TEXT.7`, while its sections retain `__TEXT` as their declared segment. The [pinned rewrite](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/src/exe_format/macho_ranges.rs) defines that exact bounded naming transformation. The decoder accepts it while still checking each section against its physical owner's permissions, virtual/file extent and address mapping. Other mismatched names remain errors. This correction follows actual emitted load commands; it does not relax range or alias validation.

The required AOT interop matrix compiles on Ubuntu, macOS and Windows hosted runners with their exact checksum-pinned compiler, then executes real development, AOT and JIT controls against the native C library/process. The aggregate gate requires every matrix job. Source/environment records and bootstrap/probe logs survive failure. A newly implemented decoder or a configured CI target does not establish that target's acceptance: its actual hosted result and retained report are required. Linux remains the existing qualified native GUI platform; this matrix is headless interoperability.

An interpreter retained for dynamic code is not a JIT fallback; Bun's [compatibility contract](https://github.com/oven-sh/bun/blob/da867c60bf0bcbf9d6d36994f8ca0efa42075115/docs/compiler/compatibility.mdx) describes runtime-generated strings as interpreted. The evidence here does not claim arbitrary unseen JavaScript is AOT-compiled, that interpreter entry is impossible, or that hardware GPU, macOS/Windows GUI, signing and installation have been qualified.
